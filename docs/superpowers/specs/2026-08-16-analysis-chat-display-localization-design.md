# 分析对话清理、计划还原与中文字段设计

## 背景与目标

当前应用在删除数据源或工作表时会删除分析运行及制品，但保留聊天消息正文，只把消息上的制品引用清空。这会让已经失效的用户需求继续显示。分析计划展示直接使用安全计划，因此筛选值会显示为脱敏令牌。模型还可能为聚合、派生和结果生成英文名称。

本次改动需要同时满足三个目标：

1. 删除数据源时，精准删除与该数据相关的用户需求、助手回复和运行历史，同时保留其他数据的对话。
2. 只在当前租户的本地界面还原分析步骤中的脱敏值；持久化计划、审计信息、模型请求和实际执行继续使用脱敏值。
3. 模型生成的新字段名和结果名称必须是中文；原始字段名保持不变。

## 方案选择

采用“运行—消息显式关联、展示层还原、规划层中文约束”的分层方案。不会仅在界面隐藏陈旧消息，也不会在删除任意数据源时清空整个会话。这样能够保持数据库状态与界面一致，同时避免误删其他数据源的分析记录或把明文写回安全计划。

## 1. 分析运行与消息关联

### 新记录

新增 `analysis_run_messages` 关联表，字段包括租户、运行 ID、消息 ID 和消息类型（`request` 或 `response`），并对运行和消息建立唯一约束。使用新表而不是直接修改已有表列，使现有 SQLite 数据库通过 `CREATE TABLE IF NOT EXISTS` 即可升级。

用户提交需求时，`ConversationService` 返回已保存的 `MessageRecord`。创建分析运行时，在同一事务内把请求消息关联为 `request`。分析完成并写入助手消息时，在保存消息的同一事务内关联该运行的 `response`。

### 删除影响闭包

文件删除和工作表删除继续先计算制品依赖闭包。在此基础上，分析运行闭包包含：

- 主数据源制品在删除闭包中的运行；
- 结果制品在删除闭包中的运行；
- 任一计划版本的 `merge.right_artifact_id` 在删除闭包中的运行。

随后计算需要删除的消息：

- `analysis_run_messages` 中与上述运行关联的消息；
- `artifact_id` 指向待删制品的助手消息；
- 对历史运行兼容：在同一会话内，选择运行创建时间之前、正文等于 `safe_request` 的最近一条用户消息。

`DeletionImpact` 和 `TableDeletionImpact` 增加不可变的 `message_ids`，并提供 `message_count`。界面确认区显示将删除的关联对话数量。

### 原子删除与回滚

确认删除时重新计算完整影响并比较，防止依赖或消息在确认后发生变化。数据库事务按以下顺序处理：

1. 删除运行—消息关联；
2. 删除关联用户需求和助手回复；
3. 删除计划版本、执行尝试和运行；
4. 对仍保留但引用待删制品的消息清空 `artifact_id`；
5. 删除策略、数据版本、制品及目标文件或工作表元数据；
6. 根据剩余消息重新生成受影响会话的 `safe_summary`；
7. 写入删除审计事件，记录消息数量但不记录消息正文。

文件仍沿用现有的暂存目录回滚机制。数据库删除失败时，文件和全部消息均恢复；不会出现文件已恢复但对话已丢失的状态。

## 2. 分析计划的授权还原展示

持久化的 `AnalysisPlan` 保持原样。`describe_plan` 增加可选的展示值解析器，只对操作中的数据值进行递归还原：

- `filter.value`；
- `fillna.values` 中的值；
- 以后出现的列表或嵌套标量值。

列名、表达式、制品 ID、结果名称和存储计划不做令牌替换。解析器只在字符串完全匹配当前租户的令牌时调用 `TokenVault.resolve`；普通字符串和找不到映射的令牌保持原样。这样不会把令牌片段错误替换到列名或表达式中。

Streamlit 运行卡片使用当前租户的解析器生成展示行。发送给分析模型的上下文、计划 JSON、数据库、审计记录和 DuckDB 执行仍只接触脱敏值。还原失败不会阻断页面，而是保留脱敏令牌。

## 3. 中文生成字段和结果名称

### 适用范围

中文命名约束只作用于模型生成的名称：

- `AnalysisPlan.result_name`；
- `GroupByOperation.aggregations[*].output`；
- `DeriveOperation.column`；
- `RenameOperation.mapping` 的目标名称；
- `MergeOperation.suffixes`，默认改为 `（"_左表", "_右表"）`。

`select`、`filter`、`sort`、`cast`、`fillna` 等操作引用的原始字段名必须保持精确，不做翻译。

### 校验规则

生成名称必须至少包含一个中日韩统一表意文字，且不能包含 ASCII 英文字母。允许数字、空格、下划线和常用中文标点。这样会拒绝 `current_revenue`、`本期_revenue`，接受“本期营收”“营收同比2026”。

系统提示词明确要求所有生成名称使用中文。模型第一次返回不合格计划时，规划器在不加入任何明文敏感值的前提下，附带具体字段路径和中文命名要求自动重试一次。第二次仍不合格时返回清晰的中文错误，不执行计划，也不通过执行后重命名掩盖问题。

## 4. 界面与错误处理

- 删除确认提示增加“关联对话 N 条”。只有存在分析、下游制品或关联消息时才要求风险确认。
- 删除成功后，消息列表和运行卡片同时消失；其他数据源的消息保持原顺序。
- 计划展示还原只影响页面文本，不改变下载、执行或审计语义。
- 中文名称校验失败时显示“模型未能生成合规的中文字段名称，请重试”，而不是通用服务不可用错误。
- 旧数据库不需要人工迁移；关联表自动创建，历史消息通过受限的会话、正文和时间匹配进行兼容清理。

## 5. 测试策略

### 删除与兼容

- 同一会话包含两个数据源的分析，删除其中一个只移除它的用户需求、助手回复、运行和结果。
- 计划把待删制品作为右侧合并源、但尚未生成结果时，仍能识别并删除该运行。
- 无显式关联的历史运行能够删除最近的匹配需求，不误删更早或其他正文消息。
- 删除影响变化或 SQLite 失败时，文件、消息、运行和会话摘要全部回滚。
- 文件级删除和工作表级删除均显示正确的消息数量。

### 安全展示

- 筛选值的已知租户令牌在计划展示中还原。
- 未知令牌、其他租户令牌、普通字符串、列名和表达式保持不变。
- 展示后重新读取数据库，计划 JSON 仍是脱敏版本。

### 中文命名

- 中文聚合输出、派生字段、重命名目标、合并后缀和结果名通过。
- 英文或中英混合的生成名称触发一次自动修正。
- 两次不合格返回明确错误且不创建可执行计划版本。
- 英文原始字段仍可被精确引用，不会被错误翻译。

## 非目标

- 不把还原后的计划或敏感值写入数据库、日志或审计事件。
- 不翻译用户原始字段名，也不对任意英文业务内容做机器翻译。
- 不删除与目标数据源无关的聊天消息。
- 不在本次改动中新增可视化图表能力。
